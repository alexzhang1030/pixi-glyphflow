# Architecture

Shared data and colorization contracts feed capability-specific density engines.

```
data layer (optional Worker)          GPU density engines (main thread)
┌──────────────────┐                ┌──────────────────────────────────────┐
│ PointStore /      │ dirty ranges  │ Pixi raster engine                   │
│ PersistentGrid    │──────────────▶│  IntensityPass instanced quads       │
│ retained source or│               │  WebGL + WebGPU baseline             │
│ fixed CIC field   │               ├──────────────────────────────────────┤
│ GridAggregator    │ snapshots     │ WebGPU density accelerator           │
│  dense/hash/CIC   │──────────────▶│  atomic CIC screen grid              │
│  or centroid      │               │  shared-memory tiled convolution     │
└──────────────────┘                └──────────────────┬───────────────────┘
                                                      │
                                      RenderTexture r16/r32float
                                                      │
                                      DecayPass → ColorizeMesh
                                      LUT 256×1 + AdaptiveController
```

Boundary rationale:

- **One public field contract feeds both density engines** — source coordinates, kernel shape, normalization, render-target formats, and colorization stay shared. `HeatmapLayer` owns engine selection and frame-level fallback. `src/intensity/webgpu/` owns WebGPU capability checks, buffer transfer, compute planning, pipelines, and resource lifetime.
- **WebGPU compute serves costly direct fields** — `webgpuDensity: "auto"` compares point count, accumulation pixels, and kernel work. Compatible retained fields use one source chunk, float accumulation, zero decay, and zero CPU aggregation. The current tiled plan covers a 1.25–16 accumulation-pixel local radius. Explicit `"raster"` and `"gather"` policies give applications deterministic control.
- **Tiled gather preserves a bounded work shape** — the bin dispatch reduces a workgroup that shares one base cell, uses a bounded workgroup hash for clustered cells, and sends the remaining Cloud-in-Cell contributions through Float32 global atomic compare/exchange. A second dispatch loads a 32×16 output tile plus a 16-pixel halo into 12 KiB of workgroup storage and evaluates the compact quadratic kernel. Packed `r16float` or `r32float` rows copy into the same Pixi RenderTexture consumed by `ColorizeMesh`.
- **Data/GPU split at the buffer boundary** — the only thing crossing is typed-array ranges. That is what makes the Worker optional rather than architectural: the same pure aggregation module runs on either side.
- **GL stays on the main thread; Workers only prepare data** — Safari's worker-WebGL support is unreliable (2D-only OffscreenCanvas in 16.4), and Pixi's WebWorkerAdapter can't save us there.
- **Two GPU draws for a 150k-point desktop replacement** — one large instanced splat into a half-float RT, then one direct LUT mesh. The direct display mesh samples the accumulation RT in layer-local UVs and removes Pixi's filter input-capture draw. Constructed, cleared, and exhausted layers keep the display mesh non-renderable, so an empty frame adds zero draws.
- **Instance capacity follows the dataset** — desktop buffers grow from 512 to 1,048,576 instances per draw, keeping one million direct splats in one accumulation draw. iOS uses a 512-instance ceiling for the historical WebKit instancing limit. A fourfold size reduction triggers a geometric shrink.
- **Aggregation chooses a bounded dense grid or exact hash fallback** — in-bounds pixel worlds use generation-stamped typed arrays; unbounded or out-of-range coordinates use the exact spatial hash. Both paths preserve insertion order and float results.
- **Typed batches are a first-class boundary** — `setRaw(Float32Array, count?)` replaces the interleaved source and `addPoints(Float32Array, count?)` appends it in bulk. Object projection stays available through `setPoints` and the object-array `addPoints` overload.
- **Trusted snapshots form the reusable streaming boundary** — `setRawTrusted(Float32Array, statistics)` borrows one complete-triple array and injects its positive-weight statistics in O(1). `PointStore` keeps the borrowed array read-only and leaves decay-age storage at base capacity, then detaches into owned data plus age storage before an append, validated replacement, or decay compaction. The layer retains the array through rebuilds and releases it on `clear()`; producers mutate it immediately before the next trusted replacement call. Retained storage with decay 0 defines this contract.
- **PointStore owns the public numeric contract** — coordinates and values must remain finite after Float32 encoding, values are non-negative, and the total positive weight must fit Float32. Zero-weight records are discarded at ingestion, so strategy selection and worker coverage operate on the active density source. Replacement validation finishes before store mutation, so rejected input preserves the current field.
- **Persistent aggregate storage owns extreme append fields** — `pointStorage: "aggregate"` validates and accumulates each batch into a fixed Cloud-in-Cell grid, then merges only its occupied nodes into a Float64 master. Retained CPU memory depends on fixed layer dimensions and cell size. `pointCount` tracks accepted representatives, `totalWeight` tracks their summed contribution, and `renderPointCount` tracks GPU splat nodes. Each weighted representative exactly encodes repeated unit points at the same coordinate. Replacement batches rebuild the grid; append batches produce additive node deltas. Resize uses a new layer because discarded source coordinates cannot be reprojected into different bounds.
- **Worker coverage belongs to HeatmapLayer** — the bridge owns one immutable in-flight request. Each request captures its source range, generation, source identity, aggregation configuration, cell size, and bounds. The layer retains `desiredEnd` and `coveredEnd`, validates all three identities on completion and again at the frame-boundary apply step, and resubmits the uncovered tail after backpressure clears.
- **Settled centroid streams converge to one field** — append batches splat immediately, then a bounded rebase policy reconciles the field after 500 ms of input idle, 32 append batches, a 5% tail of at least 1,024 points, or five seconds since the previous full result. The same source sequence and configuration settles to the same output across append batch boundaries while low-frequency streams avoid one full rebuild per point.
- **Renderer-specific uploads preserve one point source** — stable append frames leave the master GPU instance buffer untouched. A later radius, resize, normalization, or replacement rebuild synchronizes the master once from `PointStore`. WebGL copies dirty ranges into stable Pixi CPU buffers. `src/intensity/webgpu/StagingUploader.ts` copies WebGPU ranges through a four-slot mapped staging ring, submits one copy-only command buffer before density rendering, and remaps each slot asynchronously. The final vertex buffers opt out of Pixi resource GC and remain explicitly owned by `IntensityPass`, so their GPU contents stay authoritative between rebuilds.
- **WebGPU compatibility is checked at the private API boundary** — the target-format shim validates the PixiJS 8.19 renderer shape before patching it and raises a targeted compatibility error when the required internals change.
- **Accumulation storage matches the consumed field** — the splat and decay passes store summed density in one red channel, and colorization samples that channel. The single-channel target uses 2 B/pixel for `r16float`, 4 B/pixel for `r32float`, and 1 B/pixel for `r8unorm`. The format contract follows the [WebGPU plain-color capability table](https://gpuweb.github.io/gpuweb/#plain-color-formats), the [WebGL2 float color-buffer extension](https://registry.khronos.org/webgl/extensions/EXT_color_buffer_float/), and [PixiJS texture formats](https://pixijs.download/dev/docs/rendering.TEXTURE_FORMATS.html).
- **Accumulation precision is an explicit quality boundary** — `balanced` selects the existing half-float or normalized fallback. `high` selects `r32float` when WebGL exposes float blending plus linear float filtering, or when the WebGPU device exposes `float32-blendable` plus `float32-filterable`. Tiled gather accumulates in Float32 and packs once into the selected target format, so its normalization estimator follows mathematical Float32 density. The resolved format and density engine both participate in snapshot identity and normalization.
- **Heuristic optimization coordinates existing policies** — `optimization: "auto"` supplies high precision, snapshot-aware normalization, and adaptive tone mapping, then selects a deterministic profile from bounded zoom span, active point count, and renderer instance capacity. The tone curve compares the rendered peak with the source-weight geometric mean and preserves zero, peak, and ordering through a bounded power exponent. Replacement datasets refresh the structural choice. Append streams retain one profile for their source lifetime. Explicit precision, normalization, tone mapping, aggregation, resolution, and Worker values remain authoritative. Transform activity extends a 200 ms hold before adaptive-resolution evidence resumes.
- **Synchronous aggregation owns a bounded result pool** — results copy out of the shared aggregation scratch so same-frame jobs stay independent, then return to a four-buffer best-fit pool after staging. Repeated inline aggregation reaches a zero-allocation steady state.
- **Worker aggregation compacts in place** — radius-following raw snapshots use the direct staging path, centroid jobs transfer one input-sized buffer, and continuous jobs reserve one double-capacity buffer for the grid/raw blend. Results report the effective raw, grid, or blend strategy plus compression statistics. Best-fit returned buffers share a 64 MiB retention cap, bounding high-water memory across changing dataset sizes.
- **Final normalization is snapshot-scoped** — every final auto-max sample carries the source version, aggregation generation/configuration/effective strategy, covered end, dimensions, resolution scale, and accumulation format of the field it describes. A separate source-scoped zoom trajectory carries confirmed final samples across aggregation LOD keys during one gesture. Bounded zoom ranges calibrate up to nine logarithmically spaced radii including both endpoints; unbounded ranges retain the five local radius samples. Zoom replacement workers return the current-radius sample, keeping intermediate LOD latency and frame-boundary application bounded.
- **Colorization consumes summed density** — the R channel carries `Σ(k² × value)`; the public aggregation mode exposes `sum`.

The render-target format choices follow the official GPU and PixiJS capability references linked above.

## Zoom semantics: screen-stable density

`zoom` means **the display scale the layer is shown at**, and the effective kernel radius is `radius / zoom` — blobs keep a constant on-screen size at any zoom (the deck.gl `radiusPixels` model), which is what makes geographic-style data readable while zooming. The alternative (`radius * zoom`, web-map "zoom level" semantics where the data is re-projected but the layer stays screen-sized) double-scales when the layer itself is transformed: local radius × scale² on screen.

By default the layer auto-tracks its current global scale every `update()` (column length `sqrt(a²+b²)` — rotation-invariant) and re-splats on >0.1% relative change. Parented layers read that scale through `getGlobalTransform()` so a viewport scale change reaches the heatmap during the same prerender frame. This supports pixi-viewport's uniform scale and rotation directly. Non-uniform scale and skew use the transformed local x-axis magnitude; preserving a circular screen-space kernel under those transforms requires anisotropic radius support. `setZoom()` pins the value and disables tracking; `resumeAutoZoom()` re-enables it. Re-splat on zoom change is inherent to screen stability.

`minZoom` and `maxZoom` clamp the effective zoom used by kernel compensation. Auto-tracked parent scale and manual `setZoom()` share this clamp, and the public `zoom` getter reports the effective value. Pixi display transforms continue across their full range. Outside the configured range, the on-screen kernel changes with the viewport while its local radius and default aggregation cell stay bounded; this prevents extreme zoom-out from merging the field into one oversized aggregate.

With `maxIntensity: "auto"`, the normalization estimate **follows the zoom-driven radius change**. When both zoom bounds are configured, a stable full snapshot computes format-aware kernel peaks across the complete `radius / maxZoom` through `radius / minZoom` interval. Calibrated final sources with up to 1,024 splats evaluate the current radius directly on each accepted zoom frame. Larger final sources follow the logarithmically sampled trajectory, including both endpoints and the current radius, with at most nine samples. Both paths keep gesture settlement on the same color domain. A zoom replacement worker computes the current-radius peak so intermediate LODs arrive promptly. Synchronous and raw-direct paths use the same estimator locally. Final samples use the exact `RenderSnapshot` identity, and the direct small-source path additionally requires its anchor identity to match. Confirmed final samples also seed a source-scoped trajectory whose identity includes the source version, generation, coverage, dimensions, resolution scale, and accumulation format. A same-source zoom intermediate consumes trajectory prediction and transient calibration. Adaptive-resolution, target-size, accumulation-format, and source changes produce a new trajectory identity and immediate calibration.

The `r32float` estimator uses the mathematical kernel peak with unit weight scale. The `r16float` estimator refines the strongest modes at accumulation-pixel centers and reproduces the binary16 conversion after each scaled source splat. A power-of-two weight scale keeps the total positive mass at or below `32,752`, so legal high weights remain finite in the texture and the colorize domain receives the same scale. The `r8unorm` estimator quantizes and clamps every simulated blend addition. Its weight scale gives the smallest positive snapshot contribution more than one 8-bit step, producing a visible degraded field for high dynamic ranges.

Covered bounded radii use log-log interpolation from the closest confirmed trajectory pair, with the growth exponent bounded to `[0, 2]`, the strongest splat as the lower bound, and total positive splat weight as the upper bound. Unbounded and out-of-range radii use the same extrapolation, then add a refined kernel-overlap peak after 150 ms at one radius. Refined corrections above a 0.1% relative threshold cross to their target over a 120 ms log-space smoothstep on float accumulation targets. Aggregated layers retain the complete aggregation splat source and extend it as incremental batches land, so zoom normalization describes the points actually splatted into the texture. Data changes refresh direct and streaming calibration through the 250 ms throttle.

The default aggregation cell follows the effective local kernel radius at `effectiveRadius / 4`. Radius-following datasets up to 12,000 active points retain their raw splat source across zoom frames and bypass the Worker; only the kernel radius and transform evolve. From 12,000 to 20,000 points, a count smoothstep supplies a minimum raw component so the field enters continuous representation gradually. Larger datasets distribute each source point bilinearly across the four surrounding grid nodes, so node positions and weights evolve continuously as the cell size changes while conserving total weight. This continuity governs deposited mass; pixel-space residual remains data-, extent-, and Worker-timing-dependent when successive grids replace one another. A second smoothstep driven by the actual occupied-node-to-source ratio blends the grid field into raw points from `0.75` to `1.0` compression. Components below 1% are omitted, bounding the transition work at its visible contribution. The continuous aggregator uses a generation-stamped dense grid for bounded pixel worlds and a full-coordinate sparse hash for outliers and wide worlds. Effective raw fallbacks are reported to the layer and reused across later zoom frames.

Zoom-driven cell changes for the larger path rebuild at 16 ms frame cadence: the first zoom frame submits immediately, continued input updates the layer's desired configuration while one immutable Worker request remains in flight, and the current request submits as soon as backpressure clears. Generation and source identity gate same-source complete results used as render-only intermediate LODs; strategy, range, and zoom state further limit that path. Final synchronization requires the current configuration key. Each intermediate replaces the aggregation master at a frame boundary, re-splats at the live radius, and consumes transient trajectory normalization while the matching request runs. The matching final result eases toward its exact current-radius calibration, installs the snapshot-keyed sample, and extends the source trajectory. An explicit `aggregationCellSize` remains fixed in local coordinates and keeps weighted-centroid bins.

The public docs center on one live Interaction example with Manual and pixi-viewport camera drivers. Both drivers render the same 149,994-point NYC source with the same palette, zoom bounds, and `optimization: "auto"` options. Manual mode owns a small parent-container camera with anchored `toLocal()` / `toGlobal()` transforms; pixi-viewport mode lets the layer follow the plugin container. Camera and heatmap share the complete `0.6×` through `80×` fit-scale range, about `133.3×`, and resolve to the `wide-range-quality` profile: high-precision direct splats at a fixed full resolution. Four native color inputs edit the public default gradient through `setGradient()`, and an OKLCH generator produces random palettes inside the sRGB gamut. WebGPU initialization requests both float32 features required by the render target and its linear sampler.

The Aggregate capacity section feeds 1M, 100M, or 1B value-1 records through 500,000-record `addPoints()` batches into a fixed 2 px persistent grid. Its source count and total weight equal completed loop iterations while `renderPointCount` reports retained grid nodes. The field continuously sweeps 0.6×–6× zoom while panning and exposes a Manual camera with anchored wheel zoom and middle-button drag. The UI reports point counts, GPU work, native refresh, frame p95/p99, dropped-frame ratio, preparation, ingestion, and layer update. Browser verification covers both camera paths and GPU backends. CLI profilers accept up to 16M direct records and 1B aggregate records.

Adaptive-resolution changes wait for a pending aggregation replacement. Public resize records the requested dimensions while a replacement is in flight. Both paths keep the populated target bound, create the resized target on the completed replacement frame, and immediately fill it before the scene renders.

## Manual view transforms

`HeatmapLayer` exposes allocation-free view helpers for Pixi-only scenes: `moveTo` / `moveBy`, `zoomTo` / `zoomBy`, and `rotateTo` / `rotateBy`. Zoom and rotation accept an anchor in parent coordinates and preserve the local point beneath that anchor, which makes pointer-centered controls independent of `pixi-viewport`. The helpers update Pixi's ordinary position, scale, and rotation fields, so scene-graph composition and renderer culling keep their standard behavior.

Visual scale and kernel compensation have separate controls. `zoomTo` and `zoomBy` transform the layer and synchronize the screen-stable kernel immediately while auto tracking is active. `setZoom` pins kernel compensation for integrations that manage display transforms elsewhere. `setOpacity` validates a 0–1 value and writes the layer's normal Pixi alpha.

## Decay history survives rebuilds

`PointStore` records each point's birth frame. A radius, zoom, resize, or adaptive-resolution rebuild multiplies retained source weights by `retention^age` before re-splatting, so the reconstructed field matches the current ping-pong texture. Every 60 decay frames, contributions below the active texture format's precision floor are removed and the surviving history is rebased to the current frame.

## The layer's width/height are also its accumulation-texture size

`width`/`height` double as the RenderTexture pixel size (× resolution scale). They must be **pixel-magnitude numbers** — a geographic world in raw meters (NYC ≈ 54 km) asks for a 54147×51859 texture, past every GPU's 8192/16384 cap, and the splat silently renders nothing. For map-scale worlds, shrink the shared world space (the docs map demo uses 1 unit = 50 m, `WORLD_SCALE` in `InteractionDemo.client.vue`) so tiles, points and the layer all live in ~1k-unit coordinates.
